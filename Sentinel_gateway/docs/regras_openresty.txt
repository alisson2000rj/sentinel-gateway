1. VISÃO GERAL DA ARQUITETURA DO WAF
--------------------------------------------------------------------------------
O Sentinel Security Gateway é um proxy reverso programável construído sobre o
OpenResty (Nginx com LuaJIT). Ele atua na borda da aplicação (Edge Security),
posicionado entre clientes/atacantes (rede externa/Kali) e os contêineres da 
aplicação web (Apache/PHP) e banco de dados (MySQL).

O WAF intercepta cada requisição HTTP e aplica lógica de inspeção em diferentes
fases do ciclo de vida do Nginx, sem depender de modificações no código-fonte
legado da aplicação (técnica conhecida como Virtual Patching).

Ciclo de Vida das Requisições no OpenResty:
  [Cliente / Atacante]
          │
          ▼
    [1. init_by_lua_block] ── Carrega configurações e variáveis de ambiente (WAF_MODE)
          │
          ▼
    [2. access_by_lua]     ── Executa rules.lua (Regras 1 a 6 e Virtual Patching da Regra 7)
          │                   Bloqueia requisições maliciosas com HTTP 400, 403, 429
          ▼ (Se aprovado)
    [Proxy Pass]           ── Repassa a requisição limpa para o backend Apache/PHP (web:80)
          │
          ▼
    [3. header_filter]     ── Inspeciona/injeta headers (X-WAF-Mode, Set-Cookie seguro da Regra 7)
          │
          ▼
    [4. body_filter]       ── Injeta o banner informativo do WAF no HTML (banner.lua)
          │
          ▼
  [Resposta ao Cliente]

Memória Compartilhada (lua_shared_dict):
O OpenResty aloca segmentos de memória RAM compartilhados entre todos os worker
processes do Nginx:
  - waf_mode      (1 MB) : Armazena o modo global ("active" ou "passive") e o status individual de cada regra.
  - waf_config    (1 MB) : Parâmetros dinâmicos e limites das regras (limiares de taxa, tempos de bloqueio).
  - waf_rate     (10 MB) : Contadores de janelas deslizantes (Rate Limiting) indexados por IP e sessão.
  - waf_ip_block (10 MB) : Tabela de IPs atualmente bloqueados com seus respectivos TTLs (Time-To-Live).

--------------------------------------------------------------------------------
REGRA 1: IP_BLOCKLIST (Lista Negra Dinâmica de IPs)
--------------------------------------------------------------------------------
- Identificador no Código: IP_BLOCKLIST
- Fase de Execução       : access_by_lua (rules.lua)
- Categoria OWASP        : Transversal (A01 - Broken Access Control / A07 - Auth Failures)
- Status Padrão          : Ativa (quando WAF está em modo "active")

Como Funciona:
  Esta é a primeira regra executada no arquivo rules.lua. Antes de avaliar
  qualquer payload ou rota, o WAF consulta a tabela de memória compartilhada
  `block_dict` (waf_ip_block) buscando o endereço IP do cliente (ngx.var.remote_addr).

Mecânica Interna:
  1. Verifica se a regra está ativa (`is_rule_active("IP_BLOCKLIST")`).
  2. Verifica se o IP do cliente está na lista de exceções (Whitelist de Administrador
     configurada em `admin_ip_whitelist`). Se estiver, o bloqueio é ignorado.
  3. Se o IP constar em `block_dict` e não for whitelisted:
     - O WAF interrompe o processamento imediatamente.
     - Identifica a regra que gerou a punição original (armazenada como valor da chave).

Ação em caso de violação:
  - Código HTTP : 403 Forbidden
  - Header WAF  : X-WAF-Rule: IP_BLOCKLIST
  - Resposta    : Página HTML personalizada informando o IP bloqueado e a regra de origem.

Como um IP entra na Blocklist:
  Um IP é adicionado a esta lista automaticamente quando viola os limites das
  Regras 2 (Brute Force), 4 (Admin Enumeration), 5 (IDOR) ou 6 (Path Traversal),
  ou manualmente via endpoint da API (`POST /_gateway/block`).

REGRA 2: BRUTE_FORCE_LOGIN (Proteção contra Força Bruta no Login)
--------------------------------------------------------------------------------
- Identificador no Código: BRUTE_FORCE_LOGIN
- Fase de Execução       : access_by_lua (rules.lua)
- Categoria OWASP        : A07:2021 - Identification and Authentication Failures
- Alvo Monitorado        : POST /login.php

Como Funciona:
  Monitora e restringe a taxa de tentativas de autenticação enviadas para o
  endpoint de login da aplicação por um mesmo endereço IP em um intervalo de tempo.

Mecânica Interna:
  1. O WAF intercepta requisições com método POST para `/login.php`.
  2. Lê o corpo da requisição e mapeia a tentativa para a chave `bf:<IP>` no
     dicionário `waf_rate`.
  3. Utiliza a função atômica `rate_dict:incr(key, 1, 0, bf_window)`.
  4. Parâmetros dinâmicos (configuráveis via API ou Web UI):
     - `bf_limit`      : Limite máximo de requisições permitidas (Padrão: 3)
     - `bf_window`     : Janela de tempo de observação em segundos (Padrão: 3 segundos)
     - `bf_block_time` : Duração do bloqueio temporário em segundos (Padrão: 3600s / 1 hora)
  5. Se o contador exceder `bf_limit` dentro da janela:
     - O IP do cliente é registrado em `block_dict` com TTL de `bf_block_time`.
     - Adiciona o cabeçalho HTTP `Retry-After: 3600`.

Ação em caso de violação:
  - Código HTTP : 429 Too Many Requests
  - Header WAF  : X-WAF-Rule: BRUTE_FORCE_LOGIN
  - Resposta    : Bloqueio imediato indicando o excesso de tentativas e o tempo de bloqueio.

Funcionalidade Adicional de Sessão:
  Nesta mesma regra, o WAF captura o nome de usuário enviado no POST (`username`).
  Se o login for destinado ao usuário "admin", o WAF pré-associa na memória
  `waf_rate` a role "admin" ao ID de sessão (`role:<PHPSESSID>`), preparando o
  terreno para a validação de privilégios da Regra 4.

--------------------------------------------------------------------------------
ANÁLISE DE COMPATIBILIDADE, PORTABILIDADE E CUSTOMIZAÇÃO DA REGRA 2:
--------------------------------------------------------------------------------

P1: A Regra 2 funciona para qualquer aplicação pronta de fábrica ou precisa ser customizada?
R : PRECISA SER CUSTOMIZADA. A Regra 2 possui dependências diretas com a
    estrutura do Vulnbox Lab: rota `/login.php`, campo `username` e cookie
    `PHPSESSID`.

P2: A verificação do campo de formulário é necessária para o bloqueio de Força Bruta?
R : Depende da estratégia de defesa:
    - No Rate Limiting por IP (como implementado hoje): O contador `bf:<IP>` conta
      qualquer POST em `/login.php`, mesmo que venha com campos diferentes ou vazio.
    - No Mapeamento de Privilégios (Integração com a Regra 4): O WAF precisa
      obrigatoriamente extrair `post_args.username` para saber se a tentativa é do
      `admin` e associá-la à sessão.
    - Na Proteção contra Password Spraying / Ataques Distribuídos: Se o atacante usar
      múltiplos IPs para tentar a senha da mesma conta, o rate limit por IP falha.
      Para defender a conta, o WAF precisa contar tentativas por usuário
      (`bf_user:<username>`), tornando a leitura do campo mandatória.

P3: E se outra aplicação usar `email`, `user`, `login` ou `cpf` em vez de `username`?
R : O mapeamento falha! O código busca especificamente `post_args.username`.
    Se o campo for `email` (padrão de apps modernas), `post_args.username` será
    `nil`. O WAF não saberá qual usuário está tentando login e não conseguirá
    pré-atribuir a role administrativa.

P4: E se o endpoint de login for diferente (ex: `/api/auth`, `/signin`, `/wp-login.php`)?
R : A regra é completamente ignorada! O teste inicial é `if uri == "/login.php" and method == "POST"`.
    Qualquer outra rota fará o WAF ignorar o bloco, permitindo força bruta livre.

P5: E se a aplicação for uma API REST / Single Page App que envia dados em JSON?
R : O método `ngx.req.get_post_args()` retorna vazio para `Content-Type: application/json`.
    O contador de IP ainda funcionará (caso a URI seja igual), mas o campo de
    usuário não será extraído a menos que o corpo seja decodificado com `cjson.decode`.

P6: E se o cookie de sessão não for `PHPSESSID`?
R : O código busca estritamente `ngx.var.cookie_PHPSESSID`. Se a aplicação for
    feita em Python/Django (`sessionid`), Node/Express (`connect.sid`), Java
    (`JSESSIONID`) ou usar token JWT no cabeçalho `Authorization`, o WAF não
    encontrará a sessão e a amarração de privilégios falhará.

P7: Como refatorar a Regra 2 para torná-la universal?
R : 1. Suportar uma tabela de rotas prováveis de autenticação.
    2. Varrer sinônimos de campos de usuário: `{"username", "email", "login", "user", "cpf"}`.
    3. Aplicar controle duplo: por IP (`bf_ip:<IP>`) e por Conta (`bf_user:<username>`).
    4. Detectar dinamicamente o cookie ou token de sessão do framework.

REGRA 3: WEAK_PASSWORD_POLICY (Política de Senhas Fracas e Complexidade)
--------------------------------------------------------------------------------
- Identificador no Código: WEAK_PASSWORD_POLICY
- Fase de Execução       : access_by_lua (rules.lua)
- Categoria OWASP        : A07:2021 - Identification and Authentication Failures
- Alvos Monitorados      : POST /login.php           (campo: password)
                           POST /change-password.php  (campo: new_password)

Como Funciona:
  Inspeciona a senha enviada no corpo da requisição HTTP POST antes que ela seja
  repassada para a aplicação PHP ou processada pelo banco de dados, aplicando
  requisitos mínimos de segurança e higienização em nível de borda.

Mecânica Interna (Três validações sequenciais no Lua):
  1. Validação de Tamanho Mínimo:
     - Compara o comprimento `#pass` com `min_password_len` (Padrão: 8 caracteres).
     - Se `#pass < min_length`, bloqueia imediatamente com HTTP 400.
  2. Dicionário de Senhas Conhecidas / Fracas:
     - Converte a senha para minúsculas (`:lower()`) para busca case-insensitive.
     - Compara com a lista negra em memória:
       `123456`, `12345678`, `123456789`, `12345`, `password`, `qwerty`,
       `admin123`, `manager123`, `1234567`, `letmein`, `welcome`, `admin`,
       `user123`, `mudar123`, `senha123`, `a12345678`, `a123456789`.
     - Se coincidir com qualquer entrada, bloqueia com HTTP 400.
  3. Validação de Complexidade:
     - Aplica expressões regulares nativas do Lua:
       - Deve conter ao menos uma letra: `pass:find("%a")`
       - Deve conter ao menos um número: `pass:find("%d")`
     - Se faltar letra ou faltar número, bloqueia com HTTP 400.

Ação em caso de violação:
  - Código HTTP : 400 Bad Request
  - Header WAF  : X-WAF-Rule: WEAK_PASSWORD_POLICY
  - Resposta    : Mensagem descritiva explicando por que a senha foi rejeitada
                  (ex: "Senha rejeitada: possui 6 caracteres (mínimo exigido: 8)").

--------------------------------------------------------------------------------
ANÁLISE DE COMPATIBILIDADE, PORTABILIDADE E CUSTOMIZAÇÃO DA REGRA 3:
--------------------------------------------------------------------------------

P1: A Regra 3 funciona para qualquer aplicação pronta de fábrica?
R : NÃO. A Regra 3 é uma "Regra de Camada 7 Específica da Aplicação"
    (Application-Aware Rule). Ela foi escrita especificamente para o contrato de
    dados e nomes de rotas do Vulnbox Lab. Para funcionar em outra aplicação,
    ela precisa ser ajustada aos parâmetros dessa nova aplicação.

P2: Que campos de formulário ela verifica exatamente?
R : O código inspeciona exclusivamente dois nomes literais de chave:
      local pass = post_args and (post_args.password or post_args.new_password)
    - Em `/login.php`          : busca a chave `password`
    - Em `/change-password.php` : busca a chave `new_password`

P3: Se outra aplicação usar o MESMO nome de campo (`password`), ela consegue checar?
R : SIM, MAS APENAS SE:
    1. A rota for exatamente `/login.php` ou `/change-password.php`; E
    2. O método for `POST`; E
    3. O cabeçalho `Content-Type` for de formulário padrão HTML
       (`application/x-www-form-urlencoded` ou `multipart/form-data`).
    Se a outra aplicação usar o campo `password`, mas a rota for `/auth/login`,
    o WAF não executará a checagem porque o filtro de rota não dará match.

P4: Se outra aplicação usar nomes de campos DIFERENTES, ela verifica?
R : NÃO VERIFICA!
    Se uma outra aplicação chamar o campo de senha por:
    `senha`, `pass`, `passwd`, `user_password`, `secret`, `pwd`, etc.
    O comando `post_args.password` retornará `nil` (nulo em Lua).
    Como a variável `pass` será nula, o bloco `if pass then check_weak_password(pass) end`
    será ignorado silenciosamente e a requisição passará livre para o backend,
    SEM NENHUMA VALIDAÇÃO de senha fraca!

P5: E se a outra aplicação enviar dados em formato JSON (APIs REST / Single Page Apps)?
R : O WAF NÃO CONSEGUIRÁ LER A SENHA no estado atual do código!
    O comando `ngx.req.get_post_args()` do OpenResty serve apenas para decodificar
    parâmetros de formulários HTML convencionais (`application/x-www-form-urlencoded`).
    Se uma aplicação moderna (React, Angular, mobile) enviar um `POST` com:
      Content-Type: application/json
      {"username": "admin", "password": "123"}
    O `post_args` retornará vazio. Para inspecionar JSON em outra aplicação,
    o WAF precisa ser customizado para:
      1. Ler o corpo bruto: `local body = ngx.req.get_body_data()`
      2. Decodificar o JSON via biblioteca Lua: `local data = cjson.decode(body)`
      3. Extrair a senha do objeto: `local pass = data.password`

P6: Como tornar a Regra 3 genérica e reutilizável para qualquer aplicação?
R : Para torná-la universal, o script Lua deve ser refatorado para:
    a) Aceitar uma lista de rotas prováveis ou padrões de URI:
       if uri:find("login") or uri:find("auth") or uri:find("password") or uri:find("register") then ...
    b) Varrer múltiplos sinônimos de campos de senha comuns:
       local candidate_fields = {"password", "senha", "pass", "passwd", "pwd", "new_password", "new_pass", "secret"}
       for _, field in ipairs(candidate_fields) do
           if post_args[field] then pass = post_args[field]; break end
       end
    c) Detectar o Content-Type (Form vs JSON) antes de extrair os parâmetros.

P7: Considerações Importantes de Arquitetura e Produção:
    - Login vs. Cadastro/Alteração:
      Em ambientes de produção, validar regras de complexidade de senha no LOGIN
      pode gerar problemas operacionais se usuários antigos cadastraram senhas
      fracas antes da regra existir (eles ficarão impedidos de efetuar login até
      para alterar a senha). A boa prática recomenda aplicar a recusa estrita
      no Cadastro (`/register`) e na Troca (`/change-password`), enquanto no
      login aplica-se proteção contra força bruta (Regra 2).
    - Exigência de Terminação TLS (HTTPS):
      Para que o OpenResty consiga inspecionar o campo de senha no corpo do POST,
      o WAF precisa descriptografar a conexão HTTPS na borda (SSL Offloading /
      TLS Termination). Se a criptografia for ponta a ponta sem descriptografia
      no proxy reverso, o tráfego será opaco e o WAF não conseguirá inspecionar
      nenhum campo do payload.

REGRA 4: ADMIN_ENUMERATION (Proteção de Rotas Admin e Escalada Vertical)
--------------------------------------------------------------------------------
- Identificador no Código: ADMIN_ENUMERATION
- Fase de Execução       : access_by_lua (rules.lua)
- Categoria OWASP        : A01:2021 - Broken Access Control
- Alvo Monitorado        : Qualquer URI iniciando com `/admin` (ex: /admin/users.php)

Como Funciona:
  Impede que usuários não autenticados ou usuários com privilégios comuns (ex: user1)
  acessem ou enumerem painéis e funcionalidades administrativas restritas.

Mecânica Interna:
  1. O WAF detecta requisições onde `uri:sub(1, 6) == "/admin"`.
  2. Executa uma verificação dupla de privilégios:
     a) Whitelist de IP: verifica se o IP do requisitante está na lista permitida
        (`admin_ip_whitelist`, padrão: 127.0.0.1).
     b) Validação de Papel de Sessão: obtém o cookie `PHPSESSID` e consulta a role
        do usuário vinculada a essa sessão (`role:<sess_id>` em `waf_rate`).
  3. Se o IP NÃO estiver na whitelist E a sessão NÃO for de um "admin":
     - O acesso direto é rejeitado.
     - O WAF incrementa o contador de tentativas não autorizadas: `admin:<IP>`.
     - Parâmetros:
       - `admin_limit`      : Limite de tentativas suspeitas por minuto (Padrão: 3).
       - `admin_block_time` : Tempo de bloqueio do IP caso insista (Padrão: 3600 segundos).
     - Se o número de requisições exceder `admin_limit` em 60 segundos:
       - O IP é inserido na `IP_BLOCKLIST` com a flag "ADMIN_ENUMERATION".

Ação em caso de violação:
  - Tentativa única/inicial : HTTP 403 Forbidden ("Acesso negado: Rota /admin/ restrita").
  - Múltiplas tentativas    : HTTP 403 Forbidden + Inclusão do IP na `block_dict` por 1 hora.
  - Header WAF              : X-WAF-Rule: ADMIN_ACCESS_DENIED ou ADMIN_ENUMERATION

REGRA 5: IDOR_ENUMERATION (Detecção e Mitigação de Enumeração IDOR)
--------------------------------------------------------------------------------
- Identificador no Código: IDOR_ENUMERATION
- Fase de Execução       : access_by_lua (rules.lua)
- Categoria OWASP        : A01:2021 - Broken Access Control
- Alvo Monitorado        : /profile.php?id=X e /document.php?id=X

Como Funciona:
  Detecta ataques de Enumeração de Referência Direta Insegura a Objetos (IDOR),
  onde um invasor itera sequencialmente ou rapidamente sobre o parâmetro `?id=`
  para acessar dados privados de múltiplos usuários da aplicação.

Mecânica Interna:
  1. Aplica-se a requisições para `/profile.php` ou `/document.php` que possuam o parâmetro `id`.
  2. Se a requisição não for de um IP em whitelist nem de um usuário com role de admin:
     a) Rastreia a taxa de requisições por IP e URI: chave `idor_rate:<IP>:<URI>`.
     b) Rastreia o conjunto de IDs distintos acessados pelo mesmo IP: chave `idor_ids:<IP>:<URI>`.
        - Os IDs são concatenados em formato de marcadores: `|1||2||3||4|`.
        - O WAF calcula a quantidade de IDs distintos acessados na janela de 60 segundos.
  3. Parâmetros dinâmicos:
     - `idor_distinct_limit` : Quantidade máxima de IDs diferentes no minuto (Padrão: 3 IDs).
     - `idor_limit`          : Quantidade total de requisições ao endpoint no minuto (Padrão: 15).
     - `idor_block_time`     : Duração do banimento do IP (Padrão: 3600 segundos).
  4. Se o atacante acessar mais de 3 IDs distintos em menos de 1 minuto:
     - O IP é adicionado na `IP_BLOCKLIST` sob a regra `IDOR_ENUMERATION`.

Ação em caso de violação:
  - Código HTTP : 403 Forbidden
  - Header WAF  : X-WAF-Rule: IDOR_ENUMERATION
  - Resposta    : Bloqueio e adição do IP à lista negra por 1 hora.

REGRA 6: PATH_TRAVERSAL (Travessia de Diretório e Acesso a Arquivos Sensíveis)
--------------------------------------------------------------------------------
- Identificador no Código: PATH_TRAVERSAL
- Fase de Execução       : access_by_lua (rules.lua)
- Categoria OWASP        : A01:2021 - Broken Access Control
- Alvo Monitorado        : Todas as URIs e Query Strings recebidas

Como Funciona:
  Analisa o caminho completo da requisição e seus parâmetros buscando padrões de
  fuga de diretório (Directory Traversal) e tentativas de leitura de arquivos e
  pastas de configuração sensíveis da infraestrutura e do código-fonte.

Mecânica Interna:
  A requisição completa (`uri .. "?" .. query_string`) é convertida para minúsculas
  e submetida a dois tipos de inspeção:

  1. Padrões de Path Traversal (inclusive variações com URL Encoding):
     - `../`    (navegação para diretório pai padrão Linux)
     - `..\`    (navegação para diretório pai padrão Windows)
     - `%2e%2e` (codificação URL para "..")
     - `..%2f`  (combinação de ponto com barra codificada)
     - `..%5c`  (combinação de ponto com barra invertida codificada)

  2. Padrões de Arquivos e Pastas Sensíveis:
     - `^/%.env`      : Arquivos de variáveis de ambiente com senhas e segredos.
     - `^/%.git`      : Repositório de versionamento de código e metadados.
     - `^/src/`       : Código-fonte PHP interno fora da raiz pública.
     - `^/database/`  : Scripts SQL de inicialização e migração do banco.
     - `^/%.htaccess` : Configurações internas do Apache.
     - `%.sql$`       : Dumps e arquivos de banco de dados.
     - `%.bak$`       : Cópias de segurança e arquivos de backup.
     - `%.log$`       : Arquivos de log de auditoria e aplicação.

Ação em caso de violação:
  - Código HTTP : 403 Forbidden
  - Header WAF  : X-WAF-Rule: PATH_TRAVERSAL
  - Efeito      : O IP invasor é sumariamente adicionado à `IP_BLOCKLIST` por 3600s.

REGRA 7: SESSION_FIXATION_PROTECTION (Virtual Patching contra Session Fixation)
--------------------------------------------------------------------------------
- Identificador no Código: SESSION_FIXATION_PROTECTION
- Fases de Execução      : 1) access_by_lua (Entrada / rules.lua)
                           2) header_filter_by_lua_block (Saída / nginx.conf)
- Categoria OWASP        : A07:2021 - Identification and Authentication Failures
- Alvo Monitorado        : POST /login.php (Entrada) e Cookies de Resposta (Saída)

Como Funciona:
  Esta regra implementa **Virtual Patching** em nível de borda. Ela protege uma
  aplicação PHP vulnerável contra o ataque de Fixação de Sessão (Session Fixation)
  mesmo quando a aplicação em si não executa `session_regenerate_id()`.

Mecânica Interna (Operação em Duas Etapas):

  1. Etapa de Entrada (Virtual Patching em rules.lua):
     - Quando o cliente envia um `POST /login.php`, o WAF analisa os cabeçalhos HTTP.
     - Se o cabeçalho `Cookie` contiver um `PHPSESSID`, significa que um invasor pode
       ter pré-fixado esse ID no navegador da vítima antes da autenticação.
     - O OpenResty reescreve o cabeçalho `Cookie` da requisição usando regex Lua:
       `cookie_hdr:gsub("PHPSESSID=[^;%s]+;?", "")`
     - A requisição é repassada ao Apache/PHP **sem** o cookie pré-existente.
     - Efeito: Como o PHP não recebe nenhum ID de sessão no POST de login, ele é
       forçado a inicializar uma sessão completamente nova e gerar um ID aleatório
       limpo, destruindo a possibilidade de sequestro por fixação.

  2. Etapa de Saída (Endurecimento de Cookies em nginx.conf):
     - Na fase `header_filter_by_lua_block`, quando a resposta HTTP volta do backend:
     - O OpenResty inspeciona o cabeçalho `Set-Cookie`.
     - Caso contenha `PHPSESSID=`, o WAF garante a injeção forçada de duas flags:
       a) `; HttpOnly`        : Impede que o cookie seja lido via JavaScript (mitigação de XSS).
       b) `; SameSite=Strict` : Garante que o cookie não seja enviado em requisições
                                cross-site (mitigação de CSRF).

Ação em caso de ativação:
  - Requisição : Cookie pré-login removido no gateway de forma transparente.
  - Resposta   : Cabeçalho `Set-Cookie` enriquecido com `HttpOnly; SameSite=Strict`.
  - Log        : `[WAF:SESSION_FIXATION] Cookie de sessao pre-login removido no WAF.`

4. GESTÃO E CONTROLE DINÂMICO DO WAF VIA API
================================================================================
O Sentinel Gateway expõe uma interface gráfica e uma API REST na rota `/_gateway/`
que permite aos administradores e instrutores alterar parâmetros e alternar modos
sem precisar reiniciar o contêiner Docker:

- Painel de Controle Web:
  http://localhost:8080/_gateway/

- Comandos Úteis via cURL:
  * Consultar status do WAF e IPs bloqueados em tempo real:
    curl -s http://localhost:8080/_gateway/status

  * Alternar WAF global entre Ativo e Passivo:
    curl -s -X POST http://localhost:8080/_gateway/toggle

  * Ativar / Desativar uma regra específica (ex: BRUTE_FORCE_LOGIN):
    curl -s -X POST -d "rule=BRUTE_FORCE_LOGIN" http://localhost:8080/_gateway/rule/toggle

  * Desbloquear um IP manualmente (Falso Positivo):
    curl -s -X POST -d "ip=172.20.0.3" http://localhost:8080/_gateway/unblock

  * Limpar todos os contadores de taxa e bloqueios de IP:
    curl -s -X POST http://localhost:8080/_gateway/reset
